## 1. 七条反馈 → 根因 → 方案

### S8a（反馈①）阻断页只说「启动已被阻断」，无法区分原因

- **现状**：`ConflictManager.vue` 渲染 `conflict.title.blocked`「启动已被阻断」+ 描述「可重新检测，或打开诊断查看详情」。这是 S2/S4 轮用户拍板的「极简阻断页（三按钮、无破坏性列表）」设计——按当时的冲突语义（其他实例占用/归属不明）合理；但「环境缺失」（无 Docker）是**静态可判定**的事实，藏进诊断违背可感性。
- **根因**：阻断页没消费 capability report 里已有的 per-check 结果（`runtime.ts` 拿到 `report.required`，只用了 `required_ok` 布尔）。
- **方案**（按用户裁决修正：不提供一键安装按钮）：
  - `ConflictManager.vue` 阻断态内联渲染**未通过的必需检查项**（每项一行：检查名 + 状态文案，复用 doctor 的检查项文案键）。
  - Docker 缺失/未运行时给**自行安装指引文案**（引导用户安装 Docker Desktop 后重试）+ 打开诊断按钮；**不**放一键安装入口（见 S8h 裁决）。
  - 动态冲突（active_other_instance / unknown_owner）保持现有极简处置，不回退 S4 裁决。
- **验收**：无 Docker 时选工作区 → 阻断页第一屏可见「Docker 未安装/未运行」+ 自行安装指引；其余原因不再一律「启动已被阻断」。

### S8b（反馈②）大陆网络构建失败只显示「AISC CLI 返回错误」，意义不明

- **根因（已定位，两层）**：
  1. Rust `error.rs map_aisc` 缺映射：`AISC_ERR_BUILD_FAILED` / `AISC_ERR_CC_SWITCH_NETWORK` / `AISC_ERR_CC_SWITCH_RATE_LIMITED` / `AISC_ERR_GENERAL` 等全部落 `_ => ("AISC CLI 返回错误")`；真实诊断（S4/#37 已随终态事件送达的 `message`）只进 `technical_detail` 次级区，用户看不到。
  2. 无缓存首建在 #37 语义下仍硬失败（设计如此），但给用户的观感是「意义不明的失败」而非「网络受限 + 出路」。
- **方案（三层）**：
  1. `map_aisc` 补齐构建族映射（中文文案）：`AISC_ERR_BUILD_FAILED`→「镜像构建失败」，`AISC_ERR_CC_SWITCH_NETWORK`→「无法访问 GitHub（网络受限）」（retryable），`AISC_ERR_CC_SWITCH_RATE_LIMITED`→「GitHub API 限流」，`AISC_ERR_GENERAL`→「构建失败」，`AISC_ERR_CANCELLED` 等。
  2. Workbench 构建失败展示把 `technical_detail`（真实 message，含指引）提为**正文第一行**，不再折叠。
  3. **网络宽容性（#37 语义演进，2026-08-28 用户裁决：可接受）**：`aisc build` 的 cc-switch 解析失败且无任何缓存/回执时，**不再硬失败**——回退 Dockerfile 无钉分支构建（`CC_SWITCH_ASSET_URL` 为空时 Dockerfile 自带 `USE_CN_MIRROR=1` 多镜像源下载 + 显式警告「无 resolver 校验」，`docker_rebuild` 已是此语义），构建事件流显著提示「网络受限：本次构建未钉版 cc-switch（走镜像源），结果不保证可复现」。
     - 保留 `--require-pin` 开关（或等价 env）供可复现性优先的用户恢复硬失败。
- **验收**：VM 断网（可访问镜像源）场景：构建能完成且进度区有「未钉版」警示；map_aisc 映射后失败标题即人话；detail 前置。

### S8c（反馈③）等待时提示「初次构建大概需要十几分钟」

- **方案**：`BuildProgress.vue` 在首建（无上次构建日志/早期不确定阶段）显示静态提示行：「初次构建需下载基础镜像并安装依赖，通常需要 10–20 分钟，请耐心等待」。纯 i18n + 条件渲染。
- **验收**：构建等待/不确定态可见该提示；有缓存层的热重建不显示（或换「增量构建，通常几分钟」文案）。

### S8d（反馈④）初次使用必现：构建完点启动 60s 超时

- **根因（已定位）**：`runtime.py` `_READY_DEFAULT_TIMEOUT = 60.0`——就绪判定靠轮询容器内 `runtime-context.json`。弱 VM（嵌套虚拟化）**冷启动**：镜像层首次解压进页缓存 + entrypoint 首跑（工具链版本探测、cc-switch --version、`.claude.json` 恢复等）合计超 60s；热启动（OS 缓存已暖）远快于 60s。与「每次初次使用都出现」完全吻合（KI-3 轮 2.1.6 也报过同症状）。
- **方案**：
  1. **冷启动自适应超时**：该工作区+镜像组合的首次启动（registry 无成功启动记录）放宽至 **180s**；稳态保持 60s 快速失败（真坏的容器仍能尽快报错）。
  2. **等待进度事件化**：就绪等待期间每 5s 发 `runtime.start-progress` 事件（已等待秒数、阶段），UI 显示「正在启动容器… 已等待 Xs」替代静默转圈（沿用 S4 Docker 安装心跳模式）。
  3. 超时文案区分冷/热：「首次启动较慢，已等待 180s 仍未就绪」并保留自动清容器+重开自愈。
- **验收**：VM 首建后首次启动不再 60s 失败（或至少等待期有可见进度 + 超时阈值足够）；二次启动仍走 60s 快路径。

### S8e（反馈⑤）中文界面残留英文，全面清扫

- **范围（审计驱动的四类来源）**：
  1. 模板硬编码英文文案（start/cancel 类按钮）——逐 .vue 扫文本节点未走 `t()` 的；
  2. zh-CN 键缺失静默回退 en——补键或补译文；
  3. 后端枚举裸渲染——`build.progress.phase`、`progress_kind`、安装心跳 `state/phase`、web services `reason` 等已有键的核对 + 缺口补齐（前端建枚举→文案映射，后端枚举值不动——线上契约）；
  4. Rust `map_aisc`/动作按钮文案（S8b 顺带覆盖其映射新增部分）。
- **防回归**：新增 zh/en 键位齐平测试（两语言文件键集合 diff 必须为空）+ 关键枚举映射完整性测试。
- **验收**：中文界面全流程走查（picker→构建→启动→终端→探索器→设置→诊断）零英文残留（代码/路径/品牌词除外）；新增门禁进 CI。

### S8f（反馈⑥）终端 Ctrl+Shift+V 粘贴两次

- **根因（已定位）**：xterm 的 `attachCustomKeyEventHandler` 对 **keydown 与 keyup 都调用**；`Terminal.vue onTermCustomKey` 未过滤 `e.type`——Ctrl+Shift+V 在 keydown 粘贴一次，先松 V 键时 keyup 仍带 mod+shift 再粘一次（松键顺序不同才偶发单次，与「非常容易触发2次」吻合）。Ctrl+Shift+C / Ctrl+F 同病（复制/开搜索幂等所以没被察觉）。
- **方案**：`onTermCustomKey` 开头 `if (e.type !== "keydown") return true;`（一行，同时修三个组合键）。
- **验收**：焦点在终端，Ctrl+Shift+V 恰好粘贴一份（单测覆盖 type 过滤 + 现有 vitest 回归）。

### S8h（裁决新增）移除程序内一键安装 Docker 按钮

- **裁决**（2026-08-28）：砍掉初次引导后，Docker 等环境由用户自行安装解决，程序内**暂不提供一键安装按钮**。
- **方案**：
  - `OnboardingWizard.vue` 环境步：`readiness.docker === "not_installed"` 时不显示「一键安装 Docker」按钮，改自行安装指引文案（安装后重新检测）；`installed-but-stopped` 的「启动 Docker」（KI-1 静默唤起）**保留**。
  - 后端 `docker_install` / 安装心跳机制**保留**（休眠能力，"暂时"可逆）；S8a 阻断页同样只给指引不给安装按钮。
- **验收**：向导环境步与阻断页均无一键安装入口；未安装时指引清晰；已安装未启动时仍可一键启动引擎。
